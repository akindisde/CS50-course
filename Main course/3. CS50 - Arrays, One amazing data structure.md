Okay, we keep saying "compile" and "compiling" a lot, but in fact, we have ***4 steps to take the code and make it an executable file***, in this order : 

![[Pasted image 20240709145841.png]]


C code **preprocessing** is the *initial phase* in the **compilation** process of C programs. 

It involves the **transformation** of the source code before the actual compilation begins. 

This step is handled by the preprocessor, which performs several key operations : 

2. **File Inclusion**: The preprocessor handles the inclusion of header files. When you use `#include`, it effectively copies the contents of the specified file into the current file.

--> The header files are in the `/usr/include` file.

3. **Macro Expansion**: The preprocessor replaces all occurrences of defined macros with their respective values. Macros are defined using `#define`.

```c
#define PI 3.14
#define SQUARE(x) ((x) * (x))
```


	The preprocessor will replace `PI` with `3.14` and `SQUARE(x)`
	with `((x) * (x))` wherever they appear in the code.


4. **Conditional Compilation**: This allows parts of the code to be compiled or omitted based on certain conditions. This is done using directives like `#if`, `#ifdef`, `#ifndef`, `#else` `#elif`, and `#endif`. 

5. **Line Control**: This is used for error reporting and debugging, to control the line numbers and file names generated by the compiler. This is done using the `#line` directive.

6. **Comments Removal**: The preprocessor removes all comments from the source code. Both single-line (`//`) and multi-line (`/* ... */`) comments are removed.

**Compiling** is the second step in the compilation process of C programs. After preprocessing, the preprocessed source code is passed to the compiler, which performs several key tasks:

7. **Syntax and Semantic Analysis**: The compiler checks the preprocessed code for ***syntax*** errors (violations of the language's grammar rules) and ***semantic*** errors (logical errors and rule violations related to the language's meaning). This includes *type checking, variable declaration verification, and ensuring that function calls and operations are valid.*
  
8. **Intermediate Code Generation**: Once the source code passes the analysis phase, the compiler generates an **intermediate representation** (IR) of the code. This IR is a low-level, machine-independent code that serves as a bridge between the high-level source code and the machine code. The IR makes it easier to apply **optimizations** and perform further transformations.

9. **Optimization**: The compiler performs various optimizations on the intermediate code to *improve performance and reduce resource usage*. These optimizations can be classified into several types:

	- **Local Optimizations**: Optimizations that are applied within a single basic block of code, such as constant folding and common subexpression elimination.
	
	- **Global Optimizations**: Optimizations that span multiple basic blocks or functions, such as loop unrolling and function inlining.
	
	- **Machine-Independent Optimizations**: Optimizations that do not depend on the target architecture, such as dead code elimination and code motion.
	
	- **Machine-Dependent Optimizations**: Optimizations that are specific to the target architecture, such as instruction scheduling and register allocation. 

10. **Code Generation**: After optimization, the compiler generates the **target-specific machine code** from the intermediate representation. This machine code consists of instructions that can be executed directly by the target processor.

11. **Assembly**: The generated machine code is often in assembly language, which is a human-readable representation of the machine instructions. The compiler invokes an assembler to convert this assembly code into object code, which is a binary representation of the instructions. The object code is typically stored in object files with a `.o` or `.obj` extension.

 ![[Pasted image 20240709151624.png]]

The highlighted instructions are what CPU's understand which are *very low-level and basic* : 

![[Pasted image 20240709152605.png]]

Assembling is the third step in the C compilation process, following preprocessing and compiling. During this phase, the assembler converts the assembly language code generated by the compiler into machine code, producing an object file. This step is crucial because it **translates human-readable instructions into binary instructions that the computer's processor can execute.**


12. **Assembly Code Generation**: During the compilation phase, the compiler generates assembly code, which is a low-level, human-readable representation of the machine instructions. This code typically has a `.s` or `.asm` file extension.

Example of Assembly Code like the one above :

```assembly
.section .data
.LC0:
    .string "Sum: %d\n"
.section .text
.globl main
.type main, @function
main:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    $10, -4(%rbp)
    movl    $20, -8(%rbp)
    movl    -4(%rbp), %eax
    addl    -8(%rbp), %eax
    movl    %eax, -12(%rbp)
    movl    -12(%rbp), %esi
    leaq    .LC0(%rip), %rdi
    movl    $0, %eax
    call    printf
    movl    $0, %eax
    popq    %rbp
    ret

```

Of course we're not going to dive into that.

13. **Assembly**: The assembler reads the assembly code and translates it into machine code. This machine code consists of binary instructions that the CPU can execute. The assembler also resolves symbolic names and addresses used in the assembly code.
  
14. **Object File Creation**: The output of the assembler is an object file, typically with a `.o` or `.obj` extension. The object file contains machine code and additional information needed for **linking**, such as symbol tables and relocation information.

![[Pasted image 20240709153328.png]]


Linking is the final step in the C compilation process. It **combines object files produced by the assembler and resolves references between them to produce an executable file**. The linker also includes any necessary libraries and performs address resolution to ensure that all code and data references are correctly aligned in memory. 

15. **Combining Object Files**: The linker combines multiple object files generated from different source files. These object files typically have a `.o` or `.obj` extension.

16. **Resolving Symbols**: Symbols are names representing variables, functions, and data structures in the code. The linker resolves symbol references by matching symbol declarations with their definitions across all object files and libraries. ***If a symbol is declared but not defined, the linker will produce an error.***

17. **Address Binding**: The linker assigns memory addresses to code and data sections. This process includes:

    - **Code Section**: Contains executable instructions.
    
    - **Data Section**: Contains global and static variables.
    
    - **BSS Section**: Contains uninitialized global and static variables.
    
    - **Stack and Heap**: For dynamic memory allocation.

18. **Library Linking**: The linker includes standard and user-defined libraries. There are two types of linking:

    - **Static Linking**: Copies library code directly into the executable. This can result in a larger executable but ensures that all necessary code is included.
    
    - **Dynamic Linking**: Includes references to shared libraries (DLLs on Windows, .so files on Unix/Linux). The actual code is loaded at runtime, which can reduce the executable size.

19. **Relocation**: The linker adjusts address-dependent code and data to their final memory locations. This involves updating relative and absolute addresses to ensure that all references point to the correct locations in memory.
 
20. **Output Executable**: The final result of the linking process is an executable file, which can be run on the target system. This file typically has no extension on Unix/Linux systems or a `.exe` extension on Windows.

If we wanna debug a code, we need to understand the different **types of errors** we might encounter : 

21. **Syntax Errors:**
 
    - Occur when the code violates the syntax rules of the C language.
    - Examples: Missing semicolons, unmatched parentheses, incorrect usage of keywords.

22. **Semantic Errors:**
 
    - Occur when the code syntax is correct but the statements don't make logical sense.
    - Examples: Using an uninitialized variable, operations on incompatible types.

23. **Linker Errors:**

    - Occur when the linker cannot resolve references to symbols (variables or functions) during the linking phase.
    - Examples: Missing function definitions, unresolved external variables.

24. **Runtime Errors:**

    - Occur during the execution of the program.
    - Examples: Division by zero, null pointer dereference, memory allocation failures.

25. **Logical Errors:**
    
    - Occur when the program compiles and runs without crashing but produces incorrect results.
    - Examples: Incorrect algorithm implementation, wrong loop conditions.

26. **Compilation Errors:**

    - Broad category encompassing errors that prevent the program from being compiled.
    - Examples: Both syntax and semantic errors are part of compilation errors.

27. **Warnings:**

    - Not errors but indications that something might be wrong or non-standard.
    - Examples: Implicit type conversions, unused variables.

We need to know some stuff first, concerning the `main` function : 

The `main(int argc, char* argv[])` function is the entry point of a C program. It's where your program execution begins. Let's break down what each part means:

* `main`: This is the name of the function that serves as the starting point.
* `int`: This specifies the return type of the function. In this case, `main` returns an integer value, which conventionally indicates the success or failure of the program execution (0 for success, non-zero for failure).
* `argc`: This is the first argument to the `main` function. It's an integer that represents the number of arguments passed to the program when it was executed from the command line. 
* `char* argv[]`: This is the second argument to the `main` function. It's an array of character pointers (`char*`). Each element in this array points to a string (sequence of characters) that represents an argument passed to the program from the command line.

Here's an example to illustrate this:

```c
#include <stdio.h>

int main(int argc, char* argv[]) {
  printf("The program was called with %d arguments.\n", argc);
  for (int i = 0; i < argc; i++) {
    printf("Argument %d: %s\n", i + 1, argv[i]);
  }
  return 0;
}
```

Imagine you run this program from the command line like this:

```
./myprogram hello world how are you?
```

In this case:

* `argc` would be 5 (because there are 5 arguments including the program name itself)
* `argv[0]` would point to the string "./myprogram" (the program name)
* `argv[1]` would point to the string "hello"
* `argv[2]` would point to the string "world"
* and so on...

This allows your program to be flexible and takes input from the command line when it's executed. You can use `argc` and `argv` to process this input and customize your program's behavior based on the arguments provided.
